# Security controls

This page checks every control in [design §8](design.md#8-security) against
the code on `main`. For each one it records where the control is enforced
and which test proves it, or which manual check does where no automated
test can. It was written by an internal security pass before the first
public release. Findings that pass fixed are listed under
[Fixed](#fixed-in-the-security-pass); everything it left open is under
[Deferred](#deferred-and-known-gaps), with the reason. See also
[SECURITY.md](../SECURITY.md) for scope and how to report a vulnerability.

Paths are relative to the repo root. Tests are written as
`file::<test>`: unit tests live in the named source file, and
integration tests in `crates/*/tests/`. `it/` is short for
`crates/bridge/tests/it/`.

Threat classes (§8):

- **N**: someone on the phone's network;
- **P**: someone holding a stolen phone;
- **S**: a compromised push or CDN service;
- **I**: malicious content in agent output (prompt injection).

## Fixed in the security pass

1. **No per-device rate limit on actions** (§8, least privilege).
   - Before: only the unauthenticated auth endpoints were limited, so a stolen phone or a leaked token could send prompts and keys as fast as herdr accepted them.
   - Fix: `POST /v1/actions` now allows 60 actions per minute per device, then answers 429 `rate_limited` with `Retry-After` (rounded up).
   - Only a fresh key is counted, after the idempotency ledger, so replays and in-flight duplicates cost nothing and a completed action always replays its stored result. A limited key is released, so the client retries the same key; the outbox already treats `rate_limited` as retry-later.
   - `interrupt` is never limited, so Stop always works.
   - Static-token clients share one principal, so each client address gets its own budget instead.
   - Tests: `it/actions.rs::each_device_is_rate_limited_but_replays_and_interrupts_are_not`; `actions/mod.rs::static_token_clients_get_a_budget_each`; `actions/mod.rs::retry_after_rounds_up`.
2. **The audit log did not record the `choose` feedback text** (§8, audit).
   - Before: the feedback is sent to the agent as a prompt of its own, but its text and the answered `pendingId` were missing from the log.
   - Fix: both are now recorded (the text as an excerpt, like prompts).
   - Test: `audit.rs::choose_records_the_pending_id_and_the_feedback_it_sends`.
3. **Existing audit logs and audio clips kept a wide mode.** `mode(0o600)` applies only when a file is created, so an existing file stayed as it was.
   - Fix: both are now opened through `private::tighten`. It makes a regular file of the bridge's private, and refuses, with an error naming the file, a symlink (checked by comparing `lstat` with the opened file), a non-regular file, or a file the bridge cannot chmod.
   - Tests: `audit.rs::an_existing_open_log_is_tightened`; `audio/store.rs::an_existing_open_clip_is_made_private`; `private.rs::links_and_special_files_are_refused`.
4. **`devices.json` could inherit a leftover temp file's mode.** `create + truncate` reused a crashed write's temp file, along with its permissions. `devices.json` and the push store now share one helper, `private::write_atomically`, which always removes and recreates the temp file.
   - Tests: `devices.rs::a_leftover_world_readable_tmp_file_is_not_reused`; `private.rs::a_leftover_world_readable_tmp_file_is_not_reused`.
5. **A push subscribe racing a revoke could keep a revoked device subscribed** until the next restart. The store now asks whether the device is revoked under its own lock before storing. A revocation marks the device before its subscriptions are forgotten under that lock, so a racing subscribe is either refused (403) or forgotten afterwards.
   - Test: `push/store.rs::a_device_revoked_before_its_subscribe_lands_keeps_nothing`.
6. **Tool calls and diffs kept bidi and zero-width characters** (§8, untrusted rendering). They are rendered as plain text, outside the Markdown parser's cleaning, so an injected U+202E could reorder a command or a file name ("Trojan Source"). They now go through `visible_code`. It applies the same rule, but keeps tabs and line breaks for code (`\r\n` becomes `\n`). Markdown keeps its stricter predicate, so a lone CR or a decoded `&#13;` in a message still shows as U+FFFD.
   - Tests: `thread.rs::tool_calls_and_diffs_never_show_hidden_characters`; `parse.rs::code_text_keeps_tabs_and_line_breaks_only`; `parse.rs::hidden_characters_in_text_are_replaced`.
